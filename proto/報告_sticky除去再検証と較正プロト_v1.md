## 1. 概要

設計チャット20の判断（sticky kill・器具再割当）を受け、以下を実施した。

1. `sim/ring_structure/ring_sim.py`の`item_system`からsticky関連フィールドを完全除去し、
   アイテムをパドル側4種＋球側3種の7種に改訂
2. B3（球側効果稼働率）の再掃引と、確定した束での要求量64,672.2の再検証
3. `proto/ring_keep_calibration.html`（較正用プロトタイプ）を新規実装し、起動確認を実施

**結論（先出し）**：sticky除去後、リレークリア所要時間は目標23〜24分の枠内に復帰した
（中央値23.34〜23.41分）。ball_effect_magnitudeは依然として有意味化しなかった（誠実な報告）。
較正用プロトタイプは起動・操作・テレメトリ出力を確認済み。実際の較正作業（人間がパラメータを
触ってB1・B2の実測分布を求める）はこれからの人間の作業。

## 2. 作業1：sticky除去と要求量再検証

### 2-1. item_systemからのsticky除去

`ring_sim.py`の変更点：

- `ITEM_PADDLE_SIDE`から`"sticky"`を除去（`["enlarge","speed","guide","clone"]`の4種に）
- `ITEM_ALL_TYPES`の総数が7種になったことを`selfcheck.py`で検品
- ボールの状態辞書から`hold_ticks`フィールドを削除し、パドル判定ループの
  「保持中はブロック判定をスキップする」早期リターン分岐を削除（保持機構そのものが
  無くなったため、毎tick必ずブロック側の判定に到達するようになった）
- パドル側の捕球判定はシンプルな`effective_catch_rate`計算のみになり、
  sticky分岐は完全に消えた

`item_sim.py`・`item_requirement_check.py`もsticky関連の定数・引数（`sticky_hold_ticks_range`等）
を除去し、B1・B2を「参考値のみ・PASS/FAIL判定なし」で扱うよう全面改訂した
（詳細は本書§4のselfcheck検品、および§5「曖昧な指示に対する判断」参照）。

### 2-2. B3再掃引（7種均等抽選）

`item_sim.py`で`drop_rate∈{0.05,0.10,0.15,0.20,0.30}×ball_effect_ticks∈{2,3,4,5,6}`の
25組を各800試行で再掃引した（`sim/ring_structure/results/item_b3_resweep.csv`）。

| drop_rate | ball_effect_ticks=2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|
| 0.05 | 0.113 OK | 0.161 OK | 0.203 OK | 0.241 OK | 0.275 OK |
| 0.10 | 0.212 OK | 0.293 OK | 0.359 OK | 0.415 NG | 0.462 NG |
| 0.15 | 0.300 OK | 0.400 OK | 0.478 NG | 0.541 NG | 0.592 NG |
| 0.20 | 0.376 OK | 0.488 NG | 0.572 NG | 0.634 NG | 0.683 NG |
| 0.30 | 0.504 NG | 0.624 NG | 0.704 NG | 0.758 NG | 0.795 NG |

（値はB3＝球側効果いずれかが効いている時間のセッション内割合。上限0.40。OK/NGはB3判定のみ）

B3≤40%を満たすのは25組中11組。**sticky除去により、同じdrop_rate・ball_effect_ticksでも
B3（稼働率）はsticky込み時より明確に高く出る**（保持中に一時停止していた時間が丸ごと
稼働率へ加算されるようになったため）。この結果を受け、B3の成立域はsticky込み時より
狭く・低ドロップ率/短時間側に寄った。

**確定候補（FINAL_BUNDLE）：drop_rate=0.15, ball_effect_ticks=2**（B3=0.300、上限0.40に対し
margin約-25%の余裕）。`drop_rate=0.15, ball_effect_ticks=3`（B3=0.400）はちょうど境界値で
余裕がないため採用しなかった。

参考値（B1・B2はこのスクリプトの判定対象外。実測値はプロトタイプ＋プレイテストで確認）：
確定候補でのB1参考値＝平均5.36回/セッション、B2参考値（tick→秒換算）＝平均21.6秒。

**作業中に見つけた不具合（自己訂正の記録）**：`item_requirement_check.py`の`FINAL_BUNDLE`を
最初に書いた時点では、B3再掃引の実行結果を見る前に`ball_effect_ticks=4`を仮置きしていた。
その後の30試行スモークテスト、および本節の800試行本掃引の両方で、
`drop_rate=0.15, ball_effect_ticks=4`はB3=0.478（本掃引）となりB3上限（0.40）を明確に
超えることが判明したため、要求量再検証（§2-3）を実行する前に`ball_effect_ticks=2`
（B3=0.300、確認済みの合格組）へ訂正した。要求量再検証はこの訂正後の値で実行している。

### 2-3. 要求量64,672.2の再検証

確定候補束（drop_rate=0.15, ball_effect_ticks=2）で、自然3000試行・リレー300試行×
ball_effect_magnitude∈{0.5,1.0,2.0}の3水準を実行した
（`sim/ring_structure/results/item_requirement_recheck.csv`）。

| ball_effect_magnitude | natural_clear_rate | natural_damage_mean | relay_reached_frac | relay_median | relay_p90 |
|---|---|---|---|---|---|
| 0.5 | 0.0000 | 56,992.4 | 1.000 | 23.39分 | 23.74分 |
| 1.0 | 0.0000 | 57,045.7 | 1.000 | 23.41分 | 23.85分 |
| 2.0 | 0.0000 | 57,110.5 | 1.000 | 23.34分 | 23.76分 |

**単発セッション内の自然クリア率は0.0%**（想定通り。単発セッションだけではそもそも
クリアされない設計であり、リレー＝複数セッション連携でクリアする仕組みであるため、
これは異常ではない）。

**リレークリア到達率は3水準とも100%、中央値は23.34〜23.41分・p90は23.74〜23.85分**で、
目標の23〜24分の枠内に収まった。指示書05のsticky込み束では89〜92分まで膨張していたため、
**sticky除去によってリレー所要時間は正常な範囲に復帰したと言える。**

**ball_effect_magnitude（0.5/1.0/2.0）による差は、damage_meanで約57,000〜57,110、
relay_medianで23.34〜23.41分とほぼ横ばいであり、sticky除去後もball_effect_magnitudeは
有意味化しなかった。** 誠実に報告する。効果時間がball_effect_ticks=2（既に短い）で
あるため、倍率を振っても効果が乗る時間そのものが短く、累積ダメージへの寄与が
薄まっていることが要因と推測されるが、これは推測であり確定した原因分析ではない。

## 3. 較正用プロトタイプの起動確認

`proto/ring_keep_calibration.html`（単一HTML・実物理・Firebase/オンライン同期なし・
ローカル完結）を新規実装した。パドル・ボール・ブロック（強化壁相当）を1ワールド分、
`requestAnimationFrame`による実時間物理ループで実装している。

**これは計測器具であり、面白さを確かめるゲームではない。プレイテスト対象者には
見せないこと**（指示書06【やること】作業2の要求通り）。

### 3-1. 較正パネルの各項目

| スライダー | 意味 | 初期値 |
|---|---|---|
| ドロップ率 | ブロック破壊1回あたり、アイテムが落下する確率（7種から均等抽選） | 0.15 |
| サーブ間隔(秒) | 落球（ミス）してから次のボールが投入されるまでの実時間 | 2.0秒 |
| 効果時間(秒) | 球側3種（貫通・爆発・加速）が持続する実時間 | 4.0秒 |
| 効果倍率 | 球側3種の効果の強さ（貫通＝爆発範囲の半径、爆発＝範囲、加速＝速度倍率、として各アイテムで質的に異なる形で解釈される） | 1.0x |
| ボール速度(px/s) | ボールの基準速度 | 260px/s |

パドル側4種（拡大・速度・誘導・分身）は取得すると3段まで持続的に段が上がる。
球側3種（貫通・爆発・加速）は取得すると「効果時間(秒)」の間だけ時限効果として発動する。

**LIFO落球ペナルティ**：ボールをパドルで受け損ね画面下に落ちる（＝B1の1イベント）と、
パドル側の「取得順スタック」の末尾（最も新しく到達した段）を1つ取り除く。取り除かれた
段は「復帰待ち」として記録され、同じアイテムが再び同じ段まで到達した時点でB2（復帰実時間）
として記録される。

### 3-2. テレメトリの読み方

**ライブHUD**（画面上で常時更新）：経過時間・壁ダメージ（破壊ブロック累計）・パドル各段・
球側効果の残り時間・B1落球回数（累計）・B2復帰回数と直近の復帰時間・復帰待ち中の件数・
アイテム取得数（種別ごと）。

**「セッション終了・JSON出力」ボタン**を押すと、以下を含むJSONがテキストエリアに出力される。

- `config`：そのセッションで使った較正パラメータ一式
- `session_duration_sec`：セッション実時間長
- `b1_drop_count` / `b1_drop_events_sec`：B1実測（落球回数と各発生時刻）
- `b2_recovery_count` / `b2_recovery_times_sec`：B2実測（復帰回数と各復帰時間の配列）
- `b2_pending_unresolved_at_end`：セッション終了時点で未回復のまま残っていた段の数
- `item_pickup_counts` / `item_missed_pickup_count`：アイテム取得数・取りこぼし数
- `final_paddle_stages` / `final_wall_damage_block_count`：終了時点の状態

較正作業では、パラメータを変えながら複数セッションを回し、`b1_drop_events_sec`の頻度と
`b2_recovery_times_sec`の分布を、体験帯B1（2〜10回/セッション）・B2（45〜120秒）と
突き合わせることを想定している。

### 3-3. 起動確認で分かったこと・環境依存の注意

Claude Code側でブラウザ経由の起動確認を実施した。確認できたこと：

- ページ読み込み時にJSエラーが出ないこと
- 5つのスライダーが初期値通りに表示されること
- 「開始」クリックで内部状態が初期化され、「一時停止」「終了」ボタンが有効化されること
- 物理ループが実際に動作し、経過時間・壁ダメージ・B1落球回数がライブHUDに反映されること
- 「セッション終了・JSON出力」で、上記§3-2の全フィールドを含む整形されたJSONが
  出力されること

**環境依存の注意（実害なし）**：Claude Codeが使うブラウザ自動化ペインは、タブが
「非表示（`document.hidden===true`）」の状態でページを開くため、ブラウザの省電力仕様上
`requestAnimationFrame`が自然には発火しなかった。これは本プロトタイプ側の不具合ではなく、
自動化環境特有の制約であることを確認するため、`requestAnimationFrame`を`setTimeout`ベースの
代替に一時的に差し替えて動作を確認し、物理ループ・アイテム取得・LIFOペナルティ・
JSON出力のいずれも正常に機能することを検証した。**人間が実際のブラウザ（フォアグラウンドの
タブ）で開いた場合はこの制約は生じず、通常通り`requestAnimationFrame`が動作する。**
なお、起動確認時はマウスでパドルを操作していない（自動操作のため）ため、ブロック破壊数は
少なめだった。これはプロトタイプの欠陥ではなく、較正作業では人間がマウスでパドルを操作する
前提のため無関係。

## 4. selfcheck検品（成功/失敗パス分離）

`sim/ring_structure/selfcheck.py`に以下を実装・検証した（CLAUDE.md §9-c対応）。

- `check_sticky_removed`：`ITEM_PADDLE_SIDE`に`"sticky"`が含まれないこと、
  `ITEM_ALL_TYPES`の総数が7であることを検査。`--inject-instrument-bug`で`sticky`を
  人為的に混入させるとFAILすることを確認
- `check_b1_b2_have_no_verdict`：`summarize_bundle()`の出力にB1・B2のPASS/FAIL判定
  キーが存在しないこと、REFERENCE_ONLYマーク付きの参考値フィールドが存在することを検査。
  `--inject-instrument-bug`で偽の`b1_pass`キーを混入させるとFAILすることを確認
- `check_b3_evaluation_distinguishes_pass_fail`：`evaluate_b3()`が良い入力
  （稼働率0.20）でPASS、悪い入力（稼働率0.90）でFAILを正しく返すことを検査。
  `--inject-band-bug`でPASS/FAIL反転バグを注入するとFAILすることを確認

実行結果：

| 実行モード | 結果 | exit code |
|---|---|---|
| 通常実行 | RESULT: PASS | 0 |
| `--inject-band-bug` | RESULT: FAIL（2項目失敗） | 1 |
| `--inject-instrument-bug` | RESULT: FAIL（3項目失敗） | 1 |

成功パスと失敗パスが確実に異なる出力・exit codeになることを実証済み。証跡ファイルは
`sim/ring_structure/selfcheck_pass_evidence.txt`・`selfcheck_fail_band_evidence.txt`・
`selfcheck_fail_instrument_evidence.txt`ほかに保存。

## 5. 曖昧な指示に対する判断（裁量事項）

- **効果倍率（effectMagnitude）の質的解釈**：指示書は「効果時間/倍率のスライダー」とだけ
  指定しており、貫通・爆発・加速の3種にどう質的に効かせるかは指定していなかった。
  シミュレーション側（`ball_effect_magnitude`）は3種に一律の抽象倍率として扱っていたが、
  プロトタイプは「実物理で質的に異なる機構として実装する」ことが求められていたため、
  加速＝速度倍率、爆発＝破壊範囲半径、貫通＝（時限のみで倍率は直接使わず、範囲は
  爆発と共有するロジックを流用）という形で、単一スライダー値を各アイテムの文脈で
  別の意味に変換して適用した。これは指示書の「genuinely distinct mechanics」の要求を
  満たすための解釈であり、シミュレーション側の`ball_effect_magnitude`との数値的対応は
  厳密には取れていない（そもそもシミュと較正プロトタイプは別の器具であるため、対応を
  厳密化する必要性自体がないと判断した）
- **誘導（guide）・分身（clone）の実装内容**：指示書04/05素材にはこれらの具体的な
  ゲーム内挙動の定義がなかった。誘導＝ボールがパドル中心へ弱く水平方向に寄る力
  （段数に比例）、分身＝パドル左右に補助的な当たり判定を追加、として実装した。
  これらは既存の凍結事項（盤面スコープ原則・LIFO落球ペナルティ等）と矛盾しない範囲で
  独自に具体化したものであり、較正・プレイテストの結果次第で設計チャット側の調整が
  必要になる可能性がある
- **ブロック（強化壁）のHP・再生成**：指示書は「強化壁を含む」ことのみ要求していた。
  較正の主目的はB1・B2（アイテム経済のペース）であり壁の削り効率そのものではないため、
  ブロックはHP2固定・全滅時に同一グリッドで再生成する簡易実装とした
- **FINAL_BUNDLEの選定基準**：B3を満たす候補は11組あったが、境界値ぎりぎり
  （drop_rate=0.15, ticks=3のB3=0.400）ではなく、余裕のある組（ticks=2, B3=0.300）を
  選んだ。これは指示書に明記された基準ではなく、Claude Codeの裁量判断である
