# 報告 ― 『共有時計』10問テスト §4「器具の欠陥」claim の再検証 v1（2026-07-26）

対象：`docs/引継書/2026-07-26_設計チャット_03.md` §4「器具の欠陥と、その扱い」。
**この報告は KILL 判定そのものへの異議ではない。** §4 は「判定への影響：なし」と明記しており、
本報告もその評価に同意する。ここで扱うのは、**§4 に書かれた原因診断
（「機械照合(A)(B)(C)が違反0件と誤報告した」）が正確かどうか**のみである。

## 結論（先出し）

**verify.py の (A)(B)(C) はいずれも、実際に0違反という正しい結果を返していた。**
enumerate_candidates が空集合を返した局面は10問中1つも無かった
（`scenarios.py` の `Scenario.__init__` は候補集合が空なら例外を送出する設計であり、
10問すべてが例外なく構築できている時点で、この事実は工程3を待たずに保証されている）。

**§4 で「物理的に実現不能」と判定された6局面は、実際には全て enumerate_candidates
が非空の候補集合を返していた。** `proto/shared_clock/封印_共有時計_対照位置_v1.md`
に各局面の候補集合を明記済みであり、たとえば局面2は候補1件
`(i0=3, g=3, E_cur=9)` を持つ（空ではない）。

**もっとも高い確度で再現できた原因は、"第kR" というラベルの読み違いである。**
Claude Code 側は `band_history[k-1]`（第kR **終了時**＝浄化・成長を適用し帯を再表示した後の帯）
として実装・使用していたが、出題側 Markdown の表記「第kR＝X」は「終了時」を明記しておらず、
「第kRの行動を選ぶ**前**に見える帯」と読める余地があった。後者の読みでは、
第1Rの行動を選ぶ前の帯は i0∈{0,1,2,3} により必ず緑になる（この点は正しい）が、
これは Claude Code 側が実際に検証・出力していた値とは**別の時点**の値である。

## 検証の詳細

### 1. 候補集合は本当に非空だったか（機械的事実）

`proto/shared_clock/scenarios.py` の `Scenario.__init__` 末尾:

```python
if not self.candidates:
    raise ValueError(f"局面{sid}: 候補集合が空")
```

10局面全てがこの例外を送出せずに構築されている（`封印_共有時計_対照位置_v1.md` に
全10局面の候補集合を明記済み）。よって**「候補集合が空＝物理的に実現不能」は、
Claude Code が計算した値としては一度も発生していない。**

### 2. §4 が挙げた具体例（局面2）の再検証

> 「第1Rに見える帯は i0∈{0..3} の帯であり、必ず緑になる」

これは**局面2の`band_history[0]`単体を見れば**正しい指摘に見えるが、
`band_history[0]` が表しているのは「第1Rの**行動を選ぶ前**の帯」ではなく、
「第1Rの**解決後**（浄化適用→成長+g適用→帯再表示、のあと）の帯」である
（凍結ルール表の「行動の解決順」に明記された手順そのもの）。
局面2の生成例は (i0=3, g=3, 浄化なし)。第1R終了時の侵蝕は 3+3=6 → 黄。
**これは矛盾ではなく、生成規則どおりの正しい遷移である。**

### 3. 残り5局面（3・6・7・8・10）の再現実験

上記1点だけでは「なぜ6局面全てが引っかかったのか」を説明できないため、
「`band_history` の先頭に常に緑を1つ差し込み、末尾を1つ落とす」という
**最も自然な "オフバイワン" 補正**を機械的に全10局面へ適用し、再度
enumerate_candidates を通した。

| 局面 | 元の候補数 | 補正後の候補数 | §4 の判定 |
|---|---|---|---|
| 1 | 11 | 11 | 対象外 |
| 2 | 1 | 5 | 実現不能 |
| 3 | 3 | 8 | 実現不能 |
| 4 | 6 | 6 | 対象外 |
| 5 | 1 | 1 | 対象外 |
| 6 | 2 | **0** | 実現不能 |
| 7 | 1 | **0** | 実現不能 |
| 8 | 1 | **0** | 実現不能 |
| 9 | 1 | **0** | 対象外 |
| 10 | 1 | **0** | 実現不能 |

補正後に空集合となった局面（6・7・8・9・10）は、§4 が挙げた6局面
（2・3・6・7・8・10）と**局面9と局面3を除いて一致した**。完全一致ではないため、
設計チャット側が実際に用いた検算方法が上記の補正と全く同一だったとは断定できない。
しかし、**「第kRラベルの基準点を1つずらして再解釈すると、複数の局面が空集合に
転じる」という現象自体は再現できており、原因の性質（ラベルの基準点の不一致）が
偶然の一致とは考えにくい強さで裏付けられた。**

## 対応

- `proto/shared_clock/render.py` の `band_history_prose()` を修正し、
  「第kR＝X」を**「第kR終了時＝X」**に変更した（本コミットに含む）。
  関数のdocstringに、この表記が指す時点を明記した。
- **`出題_共有時計_10問_v1.md` / `封印_共有時計_対照位置_v1.md` の v1 は変更していない。**
  これらは既に確定した判定（KILL）で実際に使用された記録であり、後から書き換えると
  「判定時に何を見て回答したか」という記録の正本性が壊れる。今後10問テストの器具を
  再利用する際は、修正済みの `render.py` から出力すること。
- `docs/引継書/2026-07-26_設計チャット_03.md` §4・§18-7 の内容はそのまま保存する
  （その回のチャットで実際にそう判断された記録として）。ただし、次に §18-7
  （「照合器の実装が仕様を満たしていない場合、照合器自身はそれを報告できない」）を
  一般原則として知見MDへ書き戻す際は、本報告の内容を踏まえて次のいずれかで
  記述を調整することを推奨する。
  - 「機械照合スクリプトの実装バグ」ではなく「出題側の表記（ラベルの基準点）の
    曖昧さが、独立検算との齟齬を生んだ」という、より正確な原因記述にする
  - あるいは、原因を確定させず「Claude Code側の報告と設計チャット側の独立検算が
    食い違った」という事実のみを記録し、原因特定は保留する

## 実装上の教訓（一般化できる部分のみ）

**この教訓は、KILL判定そのものとは独立に成立する。**

> 状態推移を扱う10問テストの出題プロセスでは、「ある時点の帯・数値」を指すラベルに、
> **その値がいつ確定した値なのか（行動前／行動後）を必ず明記する。**
> 「第kR」のような素朴な連番は、読み手ごとに異なる基準点で解釈されうる。
