## 2. このチャットで確定した知見（4つ）

### 2-1.【最重要】フィルタを生成器に転用すると、出力は通過実績へ引き寄せられる

回収した §17-6 の知見だが、**引継書 01 §1-1 の診断と独立経路で同じ結論に到達している。**

- 01 §1-1：言語で検証できる基準だけが選択圧になり、それを全通過した設計だけが残る
- §17-6：フィルタを生成器に転用すると、出力が過去の通過実績へ寄る

**二重に得られた診断であり、単発の診断より強く信用してよい。**

**運用上の帰結：** KILLゲート v2.0・閉鎖超系譜リスト・禁止判定は、すべて**フィルタ**である。
これを「次に何を作るか」の入力に使う限り、出力は過去に通ったものへ寄り続ける。
**6作中3作がグループ最低評価ジャンルだった**という事実の、構造的な説明になっている。

> **規律：新系譜の着想は、フィルタの外側の座標から取る。**
> フィルタは着想を殺すためだけに使い、着想を生む側に回さない。
> （ソロ切片＝ネガティブフィルタと同じ運用を、ゲート全体に拡張する）

これは §3-1 の「通信制限付き協力」を推す理由でもある。
あれはゲート通過から出てきた案ではなく、**グループの好み分析という外部座標**から出てきた案である。

### 2-2. 知見ドキュメントの書き戻しに、ブランチを切ってはならない

同型の事故が3回発生した（§17／拘束条項インデックス／実装技術知見 §5-1d）。
いずれも「ブランチで書き戻し → マージ忘れ → 埋没」である。

照合スクリプトを増やすのは4つ目の対症療法であり、統合知見 §27 の停止条件に触れる。
**発生源はブランチそのもの。**

> **原則：docs/ 配下の Markdown は main へ直接コミットする。ブランチを切らない。**
> docs は GitHub Pages の本番挙動に影響せず、ブランチを切る利益がない。
> 一方でブランチは「マージ忘れ＝知見の埋没」という故障モードだけを生む。
> **push の人間承認ゲートは維持する**（承認ゲートはブランチではなく push が担っている）。

**この運用変更はまだ適用されていない。次チャットで CLAUDE.md への反映を判断すること。**

### 2-3. 状態を記述する文書は、1本に絞る

`現在地メモ_新チャット用.md` は、2回のバージョン跨ぎで更新漏れを起こしていた。
引継書と現在地メモという**状態文書が2本ある構造**が、正本の分岐を作り続けていた。

墓標化して廃止した（`PROJECT.md` からの参照を切らないため、削除ではなく1行の墓標に置換）。
`棚卸し_リポジトリ現状` を回収しなかったのも同じ論理である。

> **原則：状態（現在地・棚卸し）を記述する文書は、常に1本だけ存在させる。**
> 増やすたびに、正本がどれか分からなくなる。

### 2-4. 引継書は、リポジトリに置かれて初めて記録である

墓標が「現在地の正本は引継書」と宣言した一方で、
**引継書自体はチャット上にしか存在せず、§18-6（正本はリポジトリ）を満たしていなかった。**
Claude Code からの「引継書 §1-1 がどの文書か特定できない」という報告で判明した。

指示書 #5 §C で `docs/引継書/` を新設して解消した。

> **運用：引継書は発行と同時に `docs/引継書/YYYY-MM-DD_設計チャット_NN.md` として
> リポジトリへコミットする。チャットに書いた時点では、まだ記録されていない。**

## 3. 次にやるべきこと

### 3-1.【着手】通信制限付き協力 ―― 核の定義から始める

引継書 01 §3-1 の第1候補を、そのまま実行する。理由は 01 に全て書いてある（再掲しない）。
**このチャットで §2-1 が確定したことで、推す理由がもう1本増えた。**

**着手の順序（この順を崩さない）:**

**手順1. 核を1文で書く。** 次の型でなければ着手しない。

> 「〇〇するために資源 R を使うが、R は △△ にも要る」

**感情による核の定義を禁止する**（歴代6作の核は全て感情で書かれており、
盤上で何が動くかの記述が一つもなかった。これが診断の第3層である）。

**手順2. 回収した理論編の3項目を、核に当てる。**

- **A-2「仮説空間には下限もある ―― 2択への縮退」**
  → 通信制限は仮説空間を絞る操作である。絞りすぎると2択に潰れて読みが死ぬ。
    **通信制限の強さには上限がある。**この上限を先に見積もること。
- **A-3「社会的自己開示はシグナルコストとして機能する」**
  → 協力ゲームには物質的なブラフ経済がないため、
    従来のシグナル原則（コスト付き行動だけが情報を伝える）が使えないように見える。
    A-3 は、**協力ゲームでシグナルに値段を付ける手段**を与える可能性がある。ここは重点的に読む。
- **A-4「動機の多目的性の許容範囲」**
  → 協力に副次目的（個人目標・裏切り者）を足すかどうかの判断に効く。

**手順3. 着手前ゲートを通す**（引継書 01 §3-3 の7項目をそのまま適用）。
特に「ソロ版が構成できるか。できて、かつソロで退屈なら死んでいる」を必ず通すこと。
**通信制限付き協力は、この判定規則の唯一の例外**（ソロ版が原理的に構成できない）である。
逆に言えば、**ソロ版が構成できてしまう協力案は、社会層が核になっていない。**

**手順4. 10問テスト。** 手順は引継書 01 §2 に全文がある。判定基準を**結果を見る前に**凍結する。

**手順5. リモート紙同等テスト**（音声通話＋スプレッドシート、GM は設計者が手で回す）。
これは**未実行のまま残っている**。Firebase 実装は検証装置としてコストが高すぎる。
