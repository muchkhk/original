## 2. 死因（3層）

### 2-1.【決定的・直接観測】核の半分が、一度も選ばれなかった

核は「打つか送るか」だった。**送信が0回。**
「送信と行動が同じ財布から出る」という差分こそがこの案の全てだったが、
財布の片側だけで意思決定が閉じた。

### 2-2.【構造分析】受信した情報で変えられる行動が、存在しなかった

浄化は**自分の盤にしか効かない。**
仲間の帯を知っても、自分の最適行動は自分の帯だけで決まる。
市場原理（無料推定との乖離 × 判断反転時の利得 > 価格）の第2項がゼロだった。

**共有プールを作ったが、プールの使途が全て私的だった。**
資源が共有であることは、相互依存を意味しない。

**この2層が死因の骨格である。**§4 の訂正を受けても無傷。

### 2-3.【仮説・未確認】粗い要約が、隠れ変数の推定を殺した可能性

帯（緑/黄/橙）は、行動に必要な情報を全て含んでいた可能性がある。
「今どれだけ危険か」が分かれば足り、「なぜ危険か（成長率 g）」は不要だったのではないか。

> **【v2 訂正】v1 は本節に「10問中6問が物理的に実現不能だったにもかかわらず、
> 設計者は矛盾に気づかず全問を即決した」という証拠を付していた。
> §4 のとおり、この矛盾は存在しなかった。証拠は取り下げる。**

**現状：推定していた証拠も、していない証拠も無い。**
#01 §2 の「測れないものは未確認であって合格ではない」を、自分の診断にも適用し、
**本節は仮説として保持し、確定した死因として扱わない。**

『影の賽』由来の「乱数を分布未知の曖昧性へ変える」技法を協力土台へ移植した判断（(イ)）が
空振りしたかどうかは、**未確認のまま残る。**

## 3. 新しい原理 ― 1つだけ

**#02 §4-1（規律の総量を増やすな）に従い、追加は1件に絞る。**

> **原理E：通信手段を設計する前に、「受信者が、その情報によって変えられる行動」を名指しで書く。**
> 書けないなら通信は死ぬ。共有資源プールを置いても解決しない。
> **資源が共有であることと、行動が相互依存であることは別である。**
>
> **判定：** 「A が X を知った結果、A の最適行動が B から C に変わる」という文が、
> 具体的な X・B・C で書けるか。書けないなら着手しない。
>
> **本案での失敗例：** X＝仲間の帯、B・C＝浄化/送信/温存。
> **B と C が同じになる**（自分の帯が変わらない限り最適行動は変わらない）ため、文が書けなかった。
> これは着手前ゲートの7項目のどれにも引っかからなかった。

**協力ゲームに固有の落とし穴である。**
競争ゲームでは相手の情報が自分の利得に直結するため、この検査は自動的に通る。
協力ゲームでは得点が共有される一方、**行動の効果が私的なままになりやすい。**

**根拠は §2-1（直接観測）と §2-2（構造分析）であり、訂正の影響を受けない。**

## 4. 器具の欠陥 ― v1 の誤診断と、その訂正

### 4-1.【最重要】v1 の主張は誤りだった

> **v1 の記述（誤り）：** 「機械照合 (A)(B)(C) は違反0件を報告したが、実際には10問中6問が
> (i0, g) の候補集合が空＝物理的に実現不能だった。工程2の制約が効いていなかった。」

**これは誤りである。`verify.py` の0件報告は正しかった。**

Claude Code の再検証報告（`proto/shared_clock/報告_器具欠陥claim再検証_v1_2026-07-26.md`）を受け、
設計チャット側が「第kR ラベル＝第kR **終了時**（浄化→成長 適用後）」の規約で独立に再計算した結果、
**6局面すべてに候補が存在した。**局面2 は `(i0=3, g=3)` の1通りで、封印ファイルの記載と一致する。

**誤診断の原因：** 設計チャットが「第kR ラベル＝第kR の**選択時**に見えている帯」という
**自分の規約を器具に押し付け**、食い違いを器具側の欠陥と結論した。

### 4-2. 誤診断に至った手順上の失敗（3段階）

1. **食い違いを見たとき、最初に「相手の実装が誤り」を疑った。**
   正しくは「定義が一致しているか」を先に疑う
2. **封印ファイルを開けば即座に判明した。**開かない規律は「判定前」の話であり、
   §4 を書いた時点で判定は確定済みだった。**確認できたはずのものを推論で埋めた**
3. **発生源は指示書である。**記述フォーマットを例示しながら、
   帯ラベルが解決順のどの時点を指すかを定義していなかった。Code は仕様の穴を自分で埋めただけである

### 4-3. 実在した欠陥 ― そしてこれは再発である

候補集合は空ではなかったが、**帯ラベルの基準点が未定義だった**という欠陥は実在する。
Code が `render.py` を「第kR 終了時」表記へ修正済み（判定済みの v1 出力は歴史的記録として不変更）。

**これは偽装公平の器具欠陥2（○記号の多義性）と同じ病である。**
あのときは回答記号が多義だった。今回は局面記述が多義だった。

> **§18-2 の適用範囲を広げる（新原理は追加しない）：**
> **一義化の要求は、回答記号だけでなく、局面記述の全ラベルに及ぶ。**
> 特に、時点を指すラベル（「第kR」）は、解決順のどの時点かを器具側で明記する。
> **2回連続で発生している。3回目が出たら、器具の記号定義を独立の検品工程に切り出すこと。**

> **§18-7（v2 で全面改訂）：判定者による独立検算が照合器と食い違ったとき、
> 最初に疑うのは実装ではなく、定義の一致である。**
> **判定確定後は封印ファイルを開いてよい。**開けば済むものを推論で埋めない。
> （v1 の §18-7「照合器は自分の欠陥を報告できないから独立検算せよ」は、
> 独立検算の**結論の扱い方**を規定しておらず、本件の誤診断を防げなかった）

### 4-4. 残る未確認事項

**回答者（設計者）が、帯ラベルをどちらの規約で読んだかは不明である。**
器具側の規約と食い違って読んでいた可能性は残るが、
10問すべて即決という結果はどちらの規約でも変わらない。**記録のみ。**
