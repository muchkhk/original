## 3. 第9記録に使った見出しレベルと、その根拠

**`#`（h1）を使用した。**

根拠：`docs/ボードゲーム設計論_実践記録集.md`の実体を確認したところ、
「第N記録」はいずれも`#`（h1）で書かれている（例：`# 第8記録 『共有時計』(10問テストでKILL・2026-07-26)`、
`# 第7記録 「偽装公平の提案×投票採択」...`）。文書全体のタイトル自体も`#`であり、
記録見出しは文書タイトルと同じ最上位レベルを使う設計になっている。

指示書が渡した凍結テキストは`## 第9記録...`（h2）を仮に示していたが、
「見出しレベルは第8記録と同一に合わせること」の指示に従い`#`へ調整した。
**この調整に伴い、内部の`### 1./2./3./4.`（h3）サブ見出しも`## 1./2./3./4.`（h2）へ
1段繰り上げた。** 理由は5（自己判断）参照。

`add_toc.py`は`##`/`###`のみをTOC対象とする仕様のため、第8記録同様、
第9記録の記録見出し自体（h1）はTOCに載らない。内部の`## 1.〜4.`はTOCに載る
（`git diff`で確認済み）。

## 5. 自己判断で解釈を選んだ箇所（§14-7）

1. **第9記録の内部サブ見出し（`### 1.〜4.`）も、`##`（h2）へ1段繰り上げた。**
   指示書の文言は「見出し行の`#`の数のみ、上記に従って調整可」であり、
   「上記」＝「第8記録と同一レベルに合わせる」という指示は記録見出し（トップ）についてのもの。
   サブ見出しの扱いは明示されていなかった。しかし第8記録自身はトップ`#`・サブ`##`の
   1段差の階層を使っており、トップだけをh2からh1へ繰り上げてサブをh3のまま残すと
   「h1の直下にh3」という段抜けが生じ、既存の記録群と構造が食い違う。
   **第8記録との構造的整合を優先し、サブ見出しも同じ1段分繰り上げた。**
2. **`docs/引継書/2026-07-26_設計チャット_04.md`に`add_toc.py`を実行しなかった。**
   本ファイルは`# §A 引き継ぎ書` / `# §B 指示書 #D`という2つのh1で大分割し、
   手作りの2階層TOC（`§A`/`§B`をトップ、A-0〜A-7を第2階層）が指示書本文に
   埋め込まれていた。`add_toc.py`は`h2`/`h3`のみを拾いh1を拾わないため、
   これを実行すると`§A`/`§B`の区分が消え、A-0〜A-7・【目的】〜【報告してほしいこと】が
   フラットに約27項目並ぶ、著者が意図した構造と異なるTOCに置き換わる
   （`add_toc.py --check`で実際に「27見出し…更新」と出ることを確認した）。
   **B-2「本ファイルを…として収容する」を、著者が作成した文書をそのまま保存する意図と解釈し、
   TOCも含め一字一句そのまま収容した。** `add_toc.py`は第9記録を追記した実践記録集.mdと、
   §9-iを追記したCLAUDE.mdにのみ実行した。
3. **`docs/新PJ/新PJ_23_...md`（指示書#Cで修正した#15）を巻き込んだ完了条件5の解釈は
   指示書#Cの報告に既述のため、本指示書には影響しない。**
4. **完了条件8「mainへ直接コミット」の実行方法。** 詳細は6（懸念）に記載する重大な判断のため、
   自己判断としてもここに明記する。**`main`ブランチは別ワークツリーで使用中で、
   このワークツリーからチェックアウトできない**（git は同一ブランチの複数ワークツリー同時
   チェックアウトを許可しない）。そのため、コミットは引き続き現在のブランチ
   `docs/writeback-20260726`上で作成し、**承認後に`git push origin HEAD:main`で
   `origin/main`へ直接（マージコミットなしで）反映する**方式を取る予定である
   （指示書#A〜#Cで実際に使った方式と同じ）。ローカルの`git branch --show-current`は
   「main」を返さないが、**origin/main の履歴上はマージなしの直列コミットとして追加される**
   という点で、指示書の意図（ブランチ分岐によるmain埋没の再発防止）は満たしていると判断した。

## 6. 気づいた懸念

1. **【最重要】完了条件8を字義通りには満たせない構造的制約がある。**
   このリポジトリでは`main`ブランチが別のワークツリー（おそらく別セッション・別AI）で
   常時チェックアウトされており、本ワークツリーから`git checkout main`できない
   （git自体がエラーで拒否する）。指示書#Dの「ブランチを切らずmainへ直接コミットする」
   という運用は、**「mainブランチ上でコミットを作る」という文字通りの意味では、
   このマルチワークツリー構成と両立しない。** 上記5-4の代替案（現ブランチでコミット→
   push時にorigin/mainへ直接反映）で実務上の目的は達成できると判断したが、
   `git branch --show-current`が「main」を返す状態には決してならない。
   **次の指示書でこの運用を書く際は、「ローカルのmainへチェックアウトしてコミットする」
   ではなく「originのmainへマージコミットなしで直接反映する（コミット自体は
   どのローカルブランチ上で作ってもよい）」という形に文言を修正することを提案する。**
